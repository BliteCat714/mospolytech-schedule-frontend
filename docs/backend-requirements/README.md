# Требования фронтенда к бэкенду

На текущем этапе разрабатываем только фронтенд. Бэкенд не меняем; недостающие сценарии и форматы реализуем в локальных тестовых данных и mock API.

В этом документе собираем потребности для будущей интеграции. Предложения здесь не являются действующим контрактом API и не означают, что бэкенд их поддерживает.

## Запрошенные изменения

### Корректное название потока в подробностях занятия

Статус: предложение, бэкенд не изменён.

Сценарий: панель подробностей по нажатию на карточку показывает предмет, дату, время, преподавателя, место, формат, группу, поток и проект из имеющихся ответов. Для студента дополнительно показывается его группа, если группа самого занятия не указана.

В снимке `GET /api/schedule/schedule/students/{id}/?semester={id}` поле `scheduled_classes[].stream_label` для занятий без потока содержит строку вида `<method-wrapper '__str__' of NoneType object at ...>`. Фронтенд скрывает такое значение. Просьба при будущей интеграции возвращать название потока или `null`:

```json
{
  "group_name": null,
  "stream_label": null,
  "project_title": "Data Science"
}
```

Это фрагмент существующего ответа; новый маршрут и параметры не требуются. `group_name`, `stream_label` и `project_title` — строки либо `null`; отсутствие значения не является ошибкой запроса. Остальные поля и поведение пагинации остаются частью существующего контракта. Полный состав групп потока по ID фронтенд не подменяет группой текущего студента: она подписана «Ваша группа».

### Профиль по группе и общий поиск расписаний

Статус: фронтенд и моки реализованы; бэкенд не изменён.

Вход студента теперь выбирает группу, а не конкретного студента. Используются существующие `GET /api/schedule/groups/` и `GET /api/schedule/schedule/groups/{id}/?semester={id}`. В моках список групп выведен из сохранённых демо-студентов; групповое расписание составлено из общих занятий, без персональных назначений ПД и физкультуры.

Для преподавателя используются существующие `GET /api/schedule/imported/teachers/` и `GET /api/schedule/imported/teachers/{id}/schedule/`. Общая строка поиска во фронтенде объединяет группы и преподавателей. Избранные, основной профиль и открытое расписание хранятся локально, серверные изменения для них сейчас не нужны.

Для будущей интеграции при больших справочниках нужен серверный поиск с пагинацией. Предложение — `GET /api/schedule/schedule-search/?q=<запрос>&page=1&page_size=20`, публичный read-only поиск. `q` ищет номер группы либо все введённые части имени преподавателя независимо от порядка и регистра, с нормализацией «ё/е». Пока такого маршрута фронтенд не вызывает.

```json
{
  "count": 2,
  "next": null,
  "previous": null,
  "results": [
    { "kind": "group", "id": 1, "name": "ИВМ-81" },
    { "kind": "teacher", "id": 19, "name": "Александров Алексей Владимирович" }
  ]
}
```

`kind` — обязательный enum `group|teacher`, `id` — положительное целое в соответствующем справочнике, `name` — непустая строка. Отсутствие результатов: `200` с пустым `results`; неверная пагинация: стандартная ошибка API. Стабильный ключ избранного — пара `(kind, id)`, так как ID групп и преподавателей могут совпадать. Вопросы: единый источник преподавателей и привязка к актуальному импорту.

Выбор группы не устанавливает личность студента. Для персональных ПД и записи на физкультуру нужна отдельная привязка к студенту; нельзя использовать ID группы вместо `student` или автоматически выбирать первого студента. Сейчас раздел физкультуры доступен для просмотра направлений и слотов, персональная запись при групповом профиле отключена. Контракт идентификации студента требует отдельного согласования; запросы записи с групповым ID не отправляются.

## Формат требования

Для каждого требования описываем:

- Сценарий интерфейса и зачем нужны изменения.
- Существующее поведение API и недостающие данные или возможности.
- Предлагаемые метод и путь, параметры и тело запроса, если применимы.
- Пример JSON-ответа с типами, обязательностью полей и допустимостью `null`.
- Ошибки, пустое состояние, фильтрацию и пагинацию, если применимы.
- Реализацию во фронтенде и моках, статус согласования и открытые вопросы.

### Простой сценарий составления расписания ДПО

Статус: по запросу на подключение существующего генератора четырёхшаговый экран
использует действующий API. Клиентский mock-планировщик удалён; бэкенд не изменён.
Последний проверенный реальный запуск на локальной копии БД: №31, CP-SAT OPTIMAL,
1 из 1 пары в неделю, 11 фоновых пар, основное расписание №29 не изменилось.
Это проверка подключения на подготовленных данных, а не проверка полной занятости
всего вуза. Последующие проверки разработки не требуют изменения серверных данных.

Действующий контракт и потребители:

- Шаг 1: `GET /api/schedule/semesters/`, `modules/`, `runs/`, `dpo-programs/`
  и `dpo-programs/{id}/runs/`. Выбирается учебный модуль; основой служит успешный
  основной запуск того же семестра/модуля. Запуски всех программ ДПО исключаются.
  При редактировании сохраняется явно заданный допустимый `base_run`.
- Шаг 2: `GET /api/schedule/students/`, `groups/`, `dpo-memberships/`. Новые
  группы создаются как `is_dpo: true`, включение студентов выполняется через
  `POST /api/schedule/dpo-memberships/` с `{ "group": 4, "student": 61 }`.
  Основная группа студента не меняется; не вызывается PATCH студента.
- Шаг 3: существующие `subjects/`, `teachers/`, `dpo-disciplines/`; объём часов
  передаётся как `total_hours`, формат `ONLINE|ONSITE`. Часы должны делиться на
  `2 × teaching_weeks` без округления. В программе предмет уникален.
- Шаг 4: сохранение программы через существующие CRUD-методы, затем
  `POST /api/schedule/dpo-programs/{id}/plan/` с
  `{ "time_limit_seconds": 30, "seed": 17 }`. `plan` сам подготавливает нагрузку,
  отдельный вызов `prepare` пользователю не нужен. Реальный ответ содержит
  `run_id`, `status`, `scheduled_count`, `required_count`, `background_classes`.
  История читается из `dpo-programs/{id}/runs/`, строки результата — из
  `GET /api/schedule/schedule/groups/{id}/?run_id={run_id}`.

Модуль и число недель — источник периода и нагрузки; пользователь видит даты
в формате дд/мм/гггг. Результат — недельный шаблон с днями/временем, а не
придуманные календарные даты. Программы на весь семестр без модуля в новом
четырёхшаговом интерфейсе явно отмечены как неподдерживаемые и автоматически
не преобразуются в модульные. Программы с отдельным числом недель, отличным от
модуля, также не перезаписываются; при изменении периода на сервере сохранение
останавливается до обновления данных.

Изменение программ, состав слушателей и запуск требуют существующих staff-прав.
Локальный Vite dev-прокси использует отдельную серверную env-конфигурацию;
production-авторизация не изменена. Серверный CRUD не заменён клиентским обходом
прав. `400` показывает ошибки данных/подготовки, `401/403` — отсутствие доступа;
при сетевом сбое расчёта пользователю доступна проверка сохранённой истории.
Подтверждённые ID сохраняются между повторными попытками в одной вкладке.
Общий набор CRUD-запросов не атомарен; частично созданные данные не скрываются
под обещанием отката. Удаление ранее рассчитанных дисциплин/групп ограничено.

Открытый разрыв: для планирования общего объёма по произвольным датам, чётности,
праздникам и неделям нужен иной серверный контракт. Текущий API этого не обещает.
Ранее предложенный `POST /api/schedule/dpo-preview/` не реализован и не вызывается.
Также остаются вопросы обычного пользовательского доступа к составу слушателей,
идемпотентного создания и атомарного сохранения программы. Новых API в этой задаче
не добавлялось.

### Автоматическое обновление анонсов с сайта Политеха

Статус: локальная загрузка реализована только во фронтенде через dev-прокси Vite;
серверный загрузчик не реализован. Источник: https://mospolytech.ru/events/.
Проверка 09.11.2026: карточки `.card-news-wide` содержат заголовок, ссылку,
дату публикации и краткий текст; ссылка «загрузить ещё» ведёт на следующую страницу.
Дата публикации не является датой мероприятия (например, анонс конференции
от 27.10.2026 описывает проведение 7–8 декабря). Без достоверного извлечения
даты проведения оставляем `date_start: null`, показываем дату анонса и ссылку.
Не называем последние анонсы гарантированно предстоящими событиями.

Локально: фиксированный прокси `/__polytech-events` → `/events/` официального сайта,
загрузка первой страницы при открытии раздела и каждые 15 минут, ручное обновление.
Cookies и Authorization пользователя не пересылаются. При ошибке показывается
сообщение и предыдущий успешно загруженный список (если он был); архивный JSON
не подставляется под видом свежих данных. Поиск работает среди загруженных анонсов.
В production-сборке этот dev-прокси отсутствует: остаётся существующий API каталога.

Существующий контракт: `GET /api/events/` возвращает опубликованные записи из БД,
ручной импорт `POST /api/events/import/` требует административных прав. Эти методы
не означают наличия периодической синхронизации с официальным сайтом.

Предложение: фоновая серверная синхронизация раз в час (без запроса загрузки
каждым пользователем), обновление записей по каноническому URL, чтение страниц
с ограничением числа запросов и времени. Список отдавать прежним `GET /api/events/`
с существующей пагинацией и фильтрами; добавить необязательный параметр
`source=mospolytech` и поля `source_url`, `source_published_at`, `synced_at`.
Пример запроса: `GET /api/events/?source=mospolytech&page=1&page_size=20`.
Предлагаемый фрагмент ответа (остальные поля существующего контракта сохраняются):

```json
{
  "count": 1,
  "next": null,
  "previous": null,
  "results": [{
    "id": 123,
    "title": "Студенческая конференция по энергетике",
    "date_start": null,
    "date_end": null,
    "announced_at": "2026-10-27",
    "source_url": "https://mospolytech.ru/events/",
    "source_published_at": "2026-10-27",
    "synced_at": "2026-11-09T08:00:00Z"
  }]
}
```

Предложение для статуса обновления: `GET /api/events/sync-status/`, без параметров
и тела. Пример: `{"source":"mospolytech","last_success_at":"2026-11-09T08:00:00Z",
"status":"ok","stale":false}`. `status`: `ok|updating|error`, время ISO-8601
или `null`, `stale` — boolean. Недоступность источника не должна очищать каталог:
чтение последнего кэша возвращает `200`, статус показывает устаревание. `503` —
каталог/статус не могут быть прочитаны, `400` — неверные фильтры. При смене HTML
нужны обнаружение ошибки разбора и сохранение последнего успешного состояния.

Открытые вопросы: наличие официального API/RSS, правила обхода источника,
извлечение дат проведения и дедлайнов из страниц анонсов, обработка отмен,
сортировка предстоящих мероприятий и отделение архива, разумная глубина пагинации.
Предлагаемые поля и `sync-status` пока не вызываются фронтендом.
