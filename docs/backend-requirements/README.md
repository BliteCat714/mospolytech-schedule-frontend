# Требования фронтенда к бэкенду

На текущем этапе разрабатываем только фронтенд. Бэкенд не меняем; недостающие сценарии и форматы реализуем в локальных тестовых данных и mock API.

В этом документе собираем потребности для будущей интеграции. Предложения здесь не являются действующим контрактом API и не означают, что бэкенд их поддерживает.

## Запрошенные изменения

### Корректное название потока в подробностях занятия

Статус: предложение, бэкенд не изменён.

Сценарий: панель подробностей по нажатию на карточку показывает предмет, дату, время, преподавателя, место, формат, группу, поток и проект из имеющихся ответов. Для студента дополнительно показывается его группа, если группа самого занятия не указана.

В снимке `GET /api/schedule/schedule/students/{id}/?semester={id}` поле `scheduled_classes[].stream_label` для занятий без потока содержит строку вида `<method-wrapper '__str__' of NoneType object at ...>`. Фронтенд скрывает такое значение. Просьба при будущей интеграции возвращать название потока или `null`:

```json
{
  "group_name": null,
  "stream_label": null,
  "project_title": "Data Science"
}
```

Это фрагмент существующего ответа; новый маршрут и параметры не требуются. `group_name`, `stream_label` и `project_title` — строки либо `null`; отсутствие значения не является ошибкой запроса. Остальные поля и поведение пагинации остаются частью существующего контракта. Полный состав групп потока по ID фронтенд не подменяет группой текущего студента: она подписана «Ваша группа».

### Профиль по группе и общий поиск расписаний

Статус: фронтенд и моки реализованы; бэкенд не изменён.

Вход студента теперь выбирает группу, а не конкретного студента. Используются существующие `GET /api/schedule/groups/` и `GET /api/schedule/schedule/groups/{id}/?semester={id}`. В моках список групп выведен из сохранённых демо-студентов; групповое расписание составлено из общих занятий, без персональных назначений ПД и физкультуры.

Для преподавателя используются существующие `GET /api/schedule/imported/teachers/` и `GET /api/schedule/imported/teachers/{id}/schedule/`. Общая строка поиска во фронтенде объединяет группы и преподавателей. Избранные, основной профиль и открытое расписание хранятся локально, серверные изменения для них сейчас не нужны.

Для будущей интеграции при больших справочниках нужен серверный поиск с пагинацией. Предложение — `GET /api/schedule/schedule-search/?q=<запрос>&page=1&page_size=20`, публичный read-only поиск. `q` ищет номер группы либо все введённые части имени преподавателя независимо от порядка и регистра, с нормализацией «ё/е». Пока такого маршрута фронтенд не вызывает.

```json
{
  "count": 2,
  "next": null,
  "previous": null,
  "results": [
    { "kind": "group", "id": 1, "name": "ИВМ-81" },
    { "kind": "teacher", "id": 19, "name": "Александров Алексей Владимирович" }
  ]
}
```

`kind` — обязательный enum `group|teacher`, `id` — положительное целое в соответствующем справочнике, `name` — непустая строка. Отсутствие результатов: `200` с пустым `results`; неверная пагинация: стандартная ошибка API. Стабильный ключ избранного — пара `(kind, id)`, так как ID групп и преподавателей могут совпадать. Вопросы: единый источник преподавателей и привязка к актуальному импорту.

Выбор группы не устанавливает личность студента. Для персональных ПД и записи на физкультуру нужна отдельная привязка к студенту; нельзя использовать ID группы вместо `student` или автоматически выбирать первого студента. Сейчас раздел физкультуры доступен для просмотра направлений и слотов, персональная запись при групповом профиле отключена. Контракт идентификации студента требует отдельного согласования; запросы записи с групповым ID не отправляются.

## Формат требования

Для каждого требования описываем:

- Сценарий интерфейса и зачем нужны изменения.
- Существующее поведение API и недостающие данные или возможности.
- Предлагаемые метод и путь, параметры и тело запроса, если применимы.
- Пример JSON-ответа с типами, обязательностью полей и допустимостью `null`.
- Ошибки, пустое состояние, фильтрацию и пагинацию, если применимы.
- Реализацию во фронтенде и моках, статус согласования и открытые вопросы.
